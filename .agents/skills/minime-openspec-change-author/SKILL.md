# OpenSpec Change Author
Only create the next roadmap stage after the previous stage is fully closed/archived and the human explicitly advances. Use OpenSpec-native workflows. Proposal states value/non-goals; specs are observable with failure/denial scenarios; design resolves implementation-shaping choices; tasks are small/testable. Never pre-create future active changes.

When an external integration is unavailable but an existing local contingency may satisfy the acceptance behavior, assess that behavior against the Request and repository evidence. In the native feasibility report, mark the task's `fallback_assessment` as `status: fallback_applied` and `blocking: false` only when an existing local path is cited and a mapped executor Apply/Verify scenario includes focused functional verification. Otherwise report the missing behavior as blocking; do not invent or claim a fallback. Do not add a new evidence store or ask for human intervention when a sufficient contingency and verification path already exist.
