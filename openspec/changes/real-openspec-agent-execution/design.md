## Context

See `proposal.md` and the binding MM-R01 contract in `docs/backlog/MM-R01.md`. The preliminary code census confirms that `ExecutionPipelineService` currently builds prompt context and coordinates implementation/check/review/audit stages; `CliImplementerRunner` transports a prompt to a configured CLI; `OpenSpecAdapter` invokes the OpenSpec executable for validation/discovery; `WorktreeManager` already owns governed worktrees; and orchestration/PR services own durable stages and GitHub effects. The OpenSpec apply skill exists agent-side. These facts identify inspection points, not proof that any current path is safe to remove or that installed provider CLIs load the workflow.

The new capability composes the existing contracts in `primary-implementer-execution`, `reviewer-execution-contract`, `openspec-readiness`, `candidate-evidence-integrity`, `pr-preparation-and-recovery`, repository binding, durable saga, and checks. It does not replace their authorities. Codex is the available R01 implementer used to prove native apply; Antigravity is not required to demonstrate Codex execution. Canonical policy rejects a universal DeepSeek audit, while the explicitly approved R01 design adds a separate, conditional read-only reviewer role for DeepSeek only when no eligible primary reviewer can serve and capability plus explicit per-stage provider/budget authorization are verified. This authorization does not authorize any call during planning, does not alter OpenRouter policy, and never turns an existing audit result into review approval.

## Goals / Non-Goals

**Goals:**

- Deliver the R01 vertical capability and evidence for R01-S01–S07 and R01-E01–E07 from an authorized, disposable GitHub fixture through a real Draft PR and functional post-deployment check.
- Keep security, identity, permission, quota, durable-state, worktree, check, review, PR, and human-merge authority in existing mini me services.
- Make actual native agent workflow execution independently observable, with exact provider/workflow/tool version, change, worktree, attempt, candidate SHA, and redacted outcome evidence.
- Preserve N01 and all historical durable and filesystem evidence; use N01 only for a read-only before/after preservation comparison.
- Complete a Removal Ledger and remove only proven-replaced reachable implementation-prompt emulation in the same Change, after successful real-path parity and with E2E rerun after removal.

**Non-Goals:**

- Reimplement OpenSpec `propose`, `apply`, `verify`, `sync`, or `archive` semantics in Python, templates, or generic prompts.
- Replace OpenSpec parsing/readiness, worktree/GitHub/PostgreSQL/claim/check/review/PR authorities, or create a generic plugin, capability, or workflow engine.
- Implement N01, GitHub Issue-to-proposal intake (R02), post-merge closure (R04), dynamic routing, dashboard redesign, OpenRouter drain, or automatic production scheduler activation.
- Make routine DeepSeek auditing mandatory or let any auditor replace the distinct authoritative reviewer.

## Decisions

1. **Stage dispatch stays in the existing orchestration pipeline; workflow semantics stay with the installed agent.** Inspect the actual execution entry point and configured CLI profiles for each supported provider. The pipeline will dispatch a bounded request naming the exact OpenSpec change and native stage workflow; the provider-side installed skill/workflow performs the cognitive `apply`. The OpenSpec CLI remains a structural/readiness validator. Prefer extending existing runner invocation data only if the code census proves it necessary; do not add a second runner abstraction or assume Codex and Antigravity use the same command syntax.

2. **Preflight and workspace authority precede provider invocation.** Reuse durable Project/repository/Issue/change binding, current base observation, WorktreeManager and ManagedWorkspaceGuard, installed-workflow/tool discovery, and provider auth/capacity signals. A no-go or unknown prerequisite returns a structured refusal/wait before inference and before external mutation. Worktree path is supplied only by validated durable ownership. No Issue title, transcript, or agent-selected path grants authority.

   Capacity follows a provider-adapter Strategy contract; the scheduler consumes only normalized, bounded observations and contains no provider command, endpoint, path, or quota-family logic. Each observation records provider, model, account identity (redacted to a SHA-256 fingerprint in durable events), source, observation time, expiry, state, and provider-reported reset when present. Authentication and CLI availability are separate preconditions and never imply quota.

   Capacity is refreshed just in time for both primary roles before scheduler admission. Provider I/O occurs outside DB transactions/advisory locks; after acquiring the existing admission locks, the scheduler re-reads only the persisted bounded observation and fails closed if its TTL elapsed. APPLY and REVIEW each obtain their own stage-local read immediately before dispatch (the implementer observation precedes attempt creation; the reviewer observation is refreshed again after candidate checks and before REVIEW_RUNNING). A sample expiring after an already-authorized stage begins does not revoke that stage retroactively; it cannot authorize a later stage.

   Codex uses the installed App Server `account/rateLimits/read` method, never `codex exec`. It accepts only explicit boolean `ordinaryUsageAllowed` together with a non-empty active account identity and the expected Codex bucket. The App Server response has no backend timestamp, so the synchronous read is stamped locally with a maximum 60-second lifetime; percentages and reset estimates do not grant permission. Missing/null values, wrong identity/bucket, errors, and timeouts remain UNKNOWN.

   Antigravity capacity uses its native read-only `/usage` slash command in headless print mode (`agy --output-format json -p "/usage"`), which returns the structured quota data without executing an agent turn, spending tokens, or leaving a conversation behind (`num_turns: 0`, `total_tokens: 0`). This non-inferential CLI command outputs the model quota groups (specifically `Gemini Models` with `gemini-5h` and `gemini-weekly` buckets), their `remaining_fraction`, and `reset_time`. Account identity is securely obtained by directing the CLI log to an ephemeral private temporary file (`--log-file`) in a `0700` working directory, extracting the authenticated email from the silent auth initialization event (`applyAuthResult: email=...`), and computing its SHA-256 fingerprint; raw email and credentials are never stored. This design avoids the fragile settings mutation and pty requirements of the earlier statusLine experiments and eliminates races against concurrent or long-lived user sessions (such as PID 6774). Observations are bounded to a maximum 60-second TTL (identical to Codex). Missing, malformed, non-zero turn, or unparseable observations fail closed to UNKNOWN.

   On 2026-10-14, this headless `/usage` interface was validated against the installed AGY 1.3.5 binary, producing fresh non-inference observations for Gemini models (`gemini-5h` and `gemini-weekly` remaining fractions > 0) with zero turn execution and zero token consumption, successfully establishing primary reviewer capacity.

3. **Evidence requires independent observation.** Reuse existing attempt, event, candidate-manifest, check, review, and external-action persistence where it provides the required evidence. Persist only demonstrated gaps through existing PostgreSQL repositories and use Alembic if a schema addition is necessary. Corroborate native workflow use with process/tool traces plus artifact/diff and candidate observations; transcript assertions alone are insufficient. Bind check/review/PR evidence to exact candidate SHA, base SHA, generation and repository identity. Unknown external outcomes are observed/reconciled before retry.

**Candidate worktree lifecycle:** candidate-free attempts keep the existing snapshot-then-cleanup/recreation authority unchanged. Once an active Run/Job has a candidate SHA and candidate manifest, the execution pipeline retains its already-owned physical worktree through candidate review/remediation instead of transitioning ownership to `DELETED`. Re-entry is a separate read-only adoption proof: exactly one current frozen candidate must bind the active Run and Job, generation, original base, candidate ref/SHA and manifest; ownership must be `CREATED`, the path/marker/Git registration/repository binding must match, HEAD and branch ref must equal the frozen candidate, the tree must be clean and its recomputed manifest must match. Candidate evidence never enters `_verify_deleted_worktree_recreation()`. Missing/deleted ownership or any contradictory/dirty evidence fails closed and leaves existing state untouched; it is not reconstructed from the current base.

**Generated compiler and runtime artifact exclusion policy:**
- **Strict exclusion from manifest and commits:** `CandidateManifestService` and candidate preparation enforce zero tracking of generated bytecode or cache files (`__pycache__`, `*.pyc`, `*.pyo`, `.pytest_cache`, `.coverage`, etc.). Any candidate attempt that attempts to commit or stage these artifacts is rejected during manifest generation, failing closed before checks or review.
- **Check runner isolation:** `ChecksRunner` and test execution environments must isolate bytecode caching (e.g. by setting `PYTHONPYCACHEPREFIX` to an isolated ephemeral directory outside the worktree, or enforcing explicit exclusion rules). Tests executed inside candidate worktrees must not leave uncommitted `.pyc` files or cache directories behind.
- **Post-check worktree hygiene:** Immediately after check execution, worktree status is validated. If transient runtime artifacts are detected, the runner fails closed unless a sanitized remediation restores pristine worktree state matching the candidate manifest.
- **Non-destructive remediation of frozen candidates:** When an existing frozen candidate worktree contains transient, untracked runtime artifacts (e.g., from local test runner execution), remediation purges the transient files using non-destructive cleanup (`git clean -fdX` or explicit removal of transient directories) without rebasing, resetting candidate commits, mutating the frozen candidate SHA, or discarding historical attempt/event records. Re-entry verification then confirms the clean worktree matches the frozen manifest hash byte-for-byte.

4. **Candidate progression requires checks and an eligible independent reviewer.** Run configured deterministic checks and installed OpenSpec verification where supported against the frozen candidate. The normal reviewer is an eligible complementary primary, with identity independence enforced against every surviving substantive author. If no primary reviewer is eligible, DeepSeek Direct may satisfy the review gate only through a distinct reviewer contract: explicit per-stage authorization and budget, verified compatible read-only capability, exact repository/base/head/generation/manifest binding, complete review input, a schema-constrained structured response, deterministic response validation, and fail-closed handling of missing, malformed, stale, or ambiguous evidence. The existing `DeepSeekAuditorRunner` and audit records are not review authority and cannot be translated into approval. If no primary or qualifying authorized DeepSeek reviewer is available, preserve the candidate and wait. Human merge remains mandatory. Do not make any paid call without new explicit execution authorization.

5. **PR delivery reuses the existing durable GitHub path and stops at the human gate.** Reconcile the candidate branch and Draft PR through existing action reservation/observation semantics; the remote PR head must equal the audited/otherwise authorized current candidate SHA and reference the exact Issue and change. Human merge remains mandatory. No archive, automatic merge, production deploy, or closure is folded into this implementation stage.

6. **Fixture is the product acceptance boundary; N01 is a protected invariant.** Use one small explicitly authorized disposable GitHub repository with a real failing behavior test and an already READY change whose specs were authored through the agent-side OpenSpec proposal workflow. Run one bounded authorized real implementation, deterministic checks, a distinct review, and a real Draft PR. Record separate TECHNICAL_PASS, E2E_PASS and DEPLOYED_VERIFIED evidence. If inference, reviewer capacity, credentials or deployment authorization is absent, report the relevant stage NOT_VERIFIED/WAITING and do not claim complete delivery. Capture N01 read-only identity/evidence before and after; never dispatch N01 or modify its records/worktree.

7. **Removal is proof-gated and same-change.** Inventory current prompt builders, callers, runner profiles, fixtures, tests, configuration, and dynamically selected paths. Classify every affected behavior REUSE/MODIFY/REPLACE/REMOVE/RETAIN-WITH-REASON. Retire only reachable code-authoring prompt paths that the native workflow has replaced, after a real E2E proves parity. Migrate callers and valuable tests/docs, then rerun focused checks, E2E, security denials and interruption recovery after removal. Retain `OpenSpecTaskTracker`, OpenSpec validation, deterministic orchestration and other code with justified consumers; do not remove semantic proposal generation from `OpenSpecGenerator`/intake (R02) or sync/archive behavior (R04).

#### Exact current entry points and consumers

- `ExecutionPipelineService.execute_queued_job` creates the APPLY context at the `workspace_context` / `task_context` / `prompt_context` block and dispatches it through `self.implementer_runner or runner_for_implementer(current_executor)`. - `HandoffManager.format_handoff_prompt` and corrective guidance assembled from failing `CheckResult`, `ReviewFinding`, and `AuditFinding` records are recovery/diagnostic inputs. - `CliImplementerRunner.run` resolves the configured CLI profile, performs confinement and CLI preflight, projects credentials, captures redacted stdout/stderr, and enforces timeout. `runner_for_implementer` is selected dynamically from `current_executor`; keep the authority and change arguments/evidence only when required by the Codex native workflow contract.
- Configuration is read through `AppConfig.providers` / `CliInvocationConfig` and `resolve_cli_invocation` (`src/minime/config.py`); `config/minime.yaml` and `config/minime.example.yaml` define `providers.codex.invocation.implementer` as `codex exec - --approve-for-me --ephemeral` and Antigravity as a separate argument-transport CLI. `runner_for_implementer` in `implementer_runner.py` chooses from the effective `current_executor`, including reassignment; no stage may infer provider syntax from a transcript. `tests/test_worktree_and_runner.py` covers profile selection. - Candidate finalization and checks follow in `execute_queued_job`; `CandidateManifestService.generate_manifest`, configured `ChecksRunner`, `AuthorshipService`, `ReviewViewManager`, and review pipeline bind the output. Keep these authorities.
- `reviewer_contract.build_reviewer_prompt` → `CliReviewerRunner.run` / `runner_for_reviewer` is a separate read-only reviewer path. It is not an implementer prompt and is retained/extended, not removed with APPLY prompt emulation.

## Risks / Trade-offs

- **Installed Codex workflow syntax or tool-use evidence differs by version** → resolve its installed name/version in preflight and exercise the actual path; block unsupported or unobservable invocation. Antigravity is not a prerequisite for Codex acceptance.
- **DeepSeek review compatibility or independent evidence cannot be proven** → do not invoke it or convert audit output; preserve the candidate in WAITING/blocked state until an eligible primary reviewer or a verified and explicitly authorized DeepSeek review path exists.
- **Existing prompt path contains non-OpenSpec orchestration still needed for recovery or evidence** → use call-site/runtime census and ledger; remove only the semantic code-authoring portion after parity E2E and preserve safety coordination.
- **Native workflow execution can modify out-of-scope paths** → worktree confinement, path/diff checks, manifest review and fail-closed candidate validation; no PR on mismatch.
- **Provider auth/capacity or independent reviewer unavailable** → bounded preflight and wait while preserving the same Run/Job/worktree; do not consume paid fallback without explicit authority or claim E2E completion.
- **A real GitHub fixture or post-deployment target is not available** → mark the relevant E2E stage NOT_VERIFIED and block DONE; mocks/unit tests cannot substitute for product acceptance.
- **Legacy OpenSpec audit requirements conflict with canonical provider policy** → update only the affected orchestration/reviewer requirement deltas in this Change and preserve explicit policy-required audit behavior and candidate binding.
- **R01 activity overlaps currently unarchived changes or N01 recovery** → read-only reconciliation before apply; fixture isolation and no N01 mutations; seek sequencing authority if the conflict is material.

## Migration Plan

1. Before apply, verify branch/base, canonical remote and managed binding; inspect active changes, PR #140/#152, installed OpenSpec/provider workflows, relevant call graph and test fixtures. No production inference or mutation is part of this inspection.
2. Implement only the approved R01 specs, extending existing authorities and adding an Alembic migration only if a proven evidence gap requires one. Maintain backward-compatible readers and preserve all existing Run/Job/attempt/saga/worktree history.
3. Prove preflight denials and recovery first in isolated tests. Execute Codex stage E2E against the disposable GitHub fixture only with explicit provider authorization. Use an eligible complementary primary reviewer when available; otherwise use DeepSeek Direct only after its distinct read-only reviewer contract, capability, independence, and explicit per-stage budget/provider authorization have been verified. If those conditions are absent, preserve the candidate and report WAITING; publish a Draft PR only after exact candidate/check/review evidence is verified.
4. Execute the Removal Ledger after real-path parity: migrate consumers, remove superseded reachable prompt emulation, then rerun affected unit/integration, denial, interruption, stage E2E and full fixture delivery tests.
5. Merge remains human-controlled. Deploy only after authorization, run functional post-deployment fixture acceptance bound to deployed SHA/digest, and preserve rollback/evidence. If a stage cannot execute safely, stop with WAITING/BLOCKED and retain artifacts.
