## Context

See `proposal.md` and the binding MM-R01 contract in `docs/backlog/MM-R01.md`. The preliminary code census confirms that `ExecutionPipelineService` currently builds prompt context and coordinates implementation/check/review/audit stages; `CliImplementerRunner` transports a prompt to a configured CLI; `OpenSpecAdapter` invokes the OpenSpec executable for validation/discovery; `WorktreeManager` already owns governed worktrees; and orchestration/PR services own durable stages and GitHub effects. The OpenSpec apply skill exists agent-side. These facts identify inspection points, not proof that any current path is safe to remove or that installed provider CLIs load the workflow.

The new capability composes the existing contracts in `primary-implementer-execution`, `reviewer-execution-contract`, `openspec-readiness`, `candidate-evidence-integrity`, `pr-preparation-and-recovery`, repository binding, durable saga, and checks. It does not replace their authorities. Codex and Antigravity are the primary planning/execution providers selected by validated per-stage profiles and may hand off compatible work to each other with durable identity, checkpoint, fencing, and side-effect reconciliation. DeepSeek Direct is the independent reviewer for two distinct read-only stages—CONTRACT REVIEW of OpenSpec and code REVIEW of the frozen candidate. It does not plan, implement, or rescue work. OpenRouter is exceptional quota rescue for already-started work only when both primary providers are blocked by quota; it is neither a primary nor a reviewer. Review evidence never authorizes APPLY, product decisions, or human merge.

## Goals / Non-Goals

**Goals:**

- Deliver the R01 vertical capability and evidence for R01-S01–S07 and R01-E01–E07 from an authorized, disposable GitHub fixture through a real Draft PR and functional post-deployment check.
- Keep security, identity, permission, quota, durable-state, worktree, check, review, PR, and human-merge authority in existing mini me services.
- Make actual native agent workflow execution independently observable, with exact provider/workflow/tool version, change, worktree, attempt, candidate SHA, and redacted outcome evidence.
- Reuse the existing project configuration, provider adapters/capabilities, capacity observations, owner spending policy, and usage-accounting authorities to define independently configurable provider/model/effort profiles for PLAN, CONTRACT REVIEW, APPLY, TEST, VERIFY/E2E, and final REVIEW; validate every selected tuple against the exact installed CLI/version and requested native workflow.
- Start with the least-cost configured profile that satisfies documented complexity/risk and tool requirements. Keep R01 to static per-stage configuration and bounded validation; any dynamic optimization is deferred. Escalation requires objective evidence, rationale, a finite limit, and compliance with the owner's spending policy.
- Keep local AI optional and failure-isolated for preliminary complexity classification, context preparation/reduction, extraction, labeling, and auxiliary work only; it has no binding stage authority.
- Preserve N01 and all historical durable and filesystem evidence; use N01 only for a read-only before/after preservation comparison.
- Complete a Removal Ledger and remove only proven-replaced reachable implementation-prompt emulation in the same Change, after successful real-path parity and with E2E rerun after removal.

**Non-Goals:**

- Reimplement OpenSpec `propose`, `apply`, `verify`, `sync`, or `archive` semantics in Python, templates, or generic prompts.
- Replace OpenSpec parsing/readiness, worktree/GitHub/PostgreSQL/claim/check/review/PR authorities, or create a generic plugin, capability, or workflow engine.
- Implement N01, GitHub Issue-to-proposal intake (R02), post-merge closure (R04), dynamic routing, dashboard redesign, OpenRouter drain, or automatic production scheduler activation.
- Make routine DeepSeek auditing mandatory or let any auditor replace the distinct authoritative reviewer.

## Decisions

1. **Stage dispatch stays in the existing orchestration pipeline; workflow semantics stay with the installed agent.** Extend the existing project/provider configuration and invocation resolver only as required to represent a profile per stage: provider, model, effort, workflow/capability requirement, and authorized alternatives. Reuse the existing adapter registry, capacity, spending-policy, usage-accounting, and orchestration authorities; do not add a second selector, scheduler, or generic plugin framework. Validate the exact CLI/version's accepted provider/model/effort/workflow values before dispatch. Unknown compatibility is a denial, never a guessed default. Codex and AGY may serve compatible planning/execution stages according to those validated profiles; handoff between them preserves the same durable Run/Job/worktree identity, checkpoint, claims/fencing, and idempotent external-action reconciliation. DeepSeek Direct is reserved for independent read-only CONTRACT REVIEW and code REVIEW, each with separate evidence and usage accounting under its own account policy. OpenRouter can serve only exceptional rescue of already-started work after both primaries are blocked by quota; it is not a reviewer or a route around any gate. The pipeline dispatches a bounded request naming the exact OpenSpec change and native stage workflow; the installed agent-side workflow performs cognitive work. The OpenSpec CLI remains a structural/readiness validator. Do not assume Codex and AGY accept identical syntax or effort values.

   For AGY versions whose live account catalog lists effort-bearing identifiers as distinct model variants (for example, `gemini-3.8-flash-medium`), the exact listed identifier is the indivisible model/effort capability. Validate exact catalog membership and agreement between the identifier suffix and selected profile effort; pass that exact model identifier and omit a separate `--effort` override. Any conflicting profile/base CLI setting or unavailable exact variant blocks dispatch; do not substitute a neighboring variant or provider default. This derives capability only from the fresh account catalog plus the installed CLI's declared effort vocabulary, not from a model compatibility table.

   The initial profile is the lowest-cost configured candidate that meets the stage's declared complexity/risk floor and workflow/tool capability. That floor comes from existing project policy and durable change requirements or deterministic criteria; a local-AI classification may be advisory input only and cannot raise the required tier or authorize escalation. Eligibility requires exact CLI/model/effort compatibility, current stage capacity, and compliance with the owner's configured spending policy. If costs or capability are unknown, the profile is not assumed competent or cheapest. Premium models and maximum effort are not defaults. A stage may escalate only at an explicit checkpoint with objective evidence, recorded reason, bounded attempt/effort ceiling, and compliance with spending policy; R01 does not implement adaptive optimization, benchmarking, or automatic learning. Local AI may contribute preliminary complexity labels/context reduction, but those outputs are advisory and cannot independently increase effort, authorize spend, diagnose failure, implement, review security, or decide policy. Its absence/failure is non-blocking.

2. **Preflight and workspace authority precede provider invocation.** Reuse durable Project/repository/Issue/change binding, current base observation, WorktreeManager and ManagedWorkspaceGuard, installed-workflow/tool discovery, and provider auth/capacity signals. A no-go or unknown prerequisite returns a structured refusal/wait before inference and before external mutation. Worktree path is supplied only by validated durable ownership. No Issue title, transcript, or agent-selected path grants authority.

   **Intake publication preserves an already-authored OpenSpec change.** When a complete change directory exists in the durably bound managed repository, `IntakeService` loads that exact tree, validates it against the canonical artifact manifest, and copies its artifact contents to the authorized intake workspace before the existing fenced publication flow. It does not regenerate or overwrite the change from backlog prose. The recognized `.openspec.yaml` sidecar is accepted only as `spec-driven` metadata with a valid creation date; it is not an artifact created by the canonical generator and is intentionally excluded from the published artifact manifest. Symlinks, other unexpected files, unreadable/invalid UTF-8, or missing required artifacts fail closed before publication. Legacy backlog-to-OpenSpec generation remains available only when no source directory for the requested change exists. A resumed authoring action may retry only after the owned workspace proves the artifact tree and commit are absent; exact committed artifacts are adopted only when the durable ownership HEAD proves them, and partial/contradictory states remain ambiguous. Source repository contents are read-only; normal ownership, CAS, Issue binding and readiness authorities remain unchanged.

   Capacity follows a provider-adapter Strategy contract; the scheduler consumes only normalized, bounded observations and contains no provider command, endpoint, path, or quota-family logic. Each observation records provider, model, account identity (redacted to a SHA-256 fingerprint in durable events), source, observation time, expiry, state, and provider-reported reset when present. Authentication and CLI availability are separate preconditions and never imply quota.

   **Capacity, spending policy, usage accounting, and execution are separate responsibilities over one extensible adapter boundary.** Provider Capacity is authentic, fresh evidence of quota, credits, balance, or availability for a provider/account/model. Spending Policy is the owner's durable operational policy for an account/provider and may define optional limits by operation or period; it authorizes ordinary autonomous use without a new human approval for every call. Capacity or positive balance alone does not override that policy or guarantee that every operation is covered. Usage Accounting records provider-reported consumption and financial exposure durably and idempotently. Execution Strategy selects the authorized stage profile, obtains current capacity, checks applicable policy, dispatches, and reconciles reported usage. A reservation or per-operation bound is used when the configured policy or provider semantics require it, not as a universal prerequisite. Evidence and accounting remain bound to provider, protected account identity, model, stage, Run/Job, and billing origin. Provider adapters obtain capacity and usage facts from provider-supported sources; the core consumes normalized records and does not branch on provider billing details.

   Extend the existing capacity, spending-policy, and usage-accounting authorities in place; do not create parallel ledgers or selectors. Keep OpenRouter's existing pricing snapshots, policy, reservations, and historical records semantically intact. DeepSeek Direct must use only its own official account/API balance and usage evidence; OpenRouter credits, prices, reservations, or usage can never authorize or account for DeepSeek Direct, including for a DeepSeek-named model routed through OpenRouter. Any required persistence evolution is a versioned Alembic migration with existing OpenRouter rows preserved. R01 implements only provider integrations required by its authorized stages and rescue contract; other adapters remain an extension point, not opportunistic integrations. Unknown, stale, contradictory, or mismatched capacity, billing origin, or usage evidence fails closed for that operation. Unknown cost is not fabricated or treated as zero; it remains recorded as unresolved exposure while independent work may proceed if its own applicable capacity and spending policy allow it.

   The historical CONTRACT REVIEW for Run `46e123ef-5a07-43f4-9289-a2e0e0c0d891` / Job `7058b1dc-9546-4b2b-ade0-f82adeb2f69c` retains reservation `e6234837-a0ab-4a4a-9064-97f1ce28edee` as `UNRESOLVED` for USD 0.004735 reserved exposure. This is not verified actual spend and must not be settled by inference or block unrelated operations automatically.

   **Recovery after an uncertain read-only review uses a new operation, never replay.** A `REVIEW_RUNNING`, `REVIEW_PENDING`, or `REVIEW_TIMED_OUT` record is an unresolved dispatch checkpoint and blocks another request until authoritative observation resolves it. A terminal `REVIEW_FAILED` record remains immutable and, by itself, does not authorize dispatch. The same Run/Job may resume the required CONTRACT REVIEW only through canonical Control Plane `CONTINUE`, while the exact `run:<run_id>` claim/fence and its `CONTROL_PLANE` `DRIVE_CONTINUATION` decision are active. The pipeline must have no candidate and must revalidate exact project/job/change/generation/contract identity, fresh direct-account capability/capacity, verified price, and owner spending policy. It then creates a distinct Review ID, dispatch identity, and (when an optional limit requires a reservation) distinct reservation idempotency key, linked durably to the failed review; it never updates or settles the old review/reservation. Prior `UNRESOLVED` exposure remains preserved and is counted against any applicable configured limit. A completed review with `CONTRACT_CHANGES_REQUIRED`, contradictory identity, an active/ambiguous review, missing current fence, or existing candidate cannot be retried this way. Repeated CONTINUE after the new operation enters `REVIEW_RUNNING` observes that checkpoint and does not dispatch again. If eligibility or spending policy denies the operation, the same Run/Job preserves its checkpoint and waits; no backlog lifecycle state is fabricated and no second Run/Job is admitted.

   **A failed acknowledgment after a committed execution checkpoint permits only a new fenced continuation.** Control Plane may expose CONTINUE for an otherwise-active Run only when its exact active Job is `CHECKS_FAILED`, the unique latest durable attempt is completed and matches `job.attempt_count`, `job.candidate_sha` exactly matches that attempt's `end_sha`, `run.current_candidate_sha` is absent, and the latest matching `CONTROL_PLANE` `RESUME_SAFE_CHECKPOINT` / `DRIVE_CONTINUATION` decision remains `EXECUTING` under an expired or released claim. A subsequent failed CONTINUE record must match Run/project/change and current precondition stage; a legacy null `job_id` is accepted only through the Run's current `active_job_id`, while a contradictory non-null Job ID is denied. Pending/running/timed-out reviews, frozen candidates, unresolved external actions, stale/missing decisions, live claims, mismatched attempts or candidate SHA deny the exception. A new operator action request ID acquires a new current claim/fence and reruns normal repository, worktree, stage, capacity and idempotency guards; the prior action/decision/attempt are immutable. This exception never permits blind replay of a paid or external operation.

   **A failed read-only review may reconstruct its deleted worktree only from a planning-only recovery snapshot.** This exception is limited to the same exact Run/Job with no candidate, no durable implementation attempts, and only terminal failed CONTRACT REVIEW records for the exact OpenSpec contract. A unique `WORKTREE_RECOVERY_SNAPSHOT` event must bind the canonical project/job/run/change/path/branch to one snapshot SHA and explicitly state `authoritative_candidate=false`; the branch commit must have the original durable base as its sole parent and contain only the exact published OpenSpec manifest for that change. The normal repository binding, remote-base ancestry/identity, ownership marker/path, Git registration, publication-manifest, claim/fence, and side-effect checks still apply. The snapshot branch and original base identity are preserved. Missing/ambiguous review, event, manifest, branch, or remote evidence fails closed. This path does not authorize general deleted-worktree recreation and does not relax candidate-free attempt requirements for other recovery causes.

   Capacity is refreshed just in time for the provider/model selected for the stage about to execute. Admission validates durable policy/profile and the initial stage's capacity; future-stage capacity is refreshed at that stage boundary, outside DB transactions/advisory locks, then re-read under existing locks before dispatch and denied if its TTL elapsed. CONTRACT REVIEW, APPLY, TEST, VERIFY/E2E, and final REVIEW each use their own stage-local eligibility and budget check. Reviewer capacity is refreshed immediately before the corresponding read-only review. A sample expiring after an already-authorized stage begins does not revoke that stage retroactively; it cannot authorize a later stage. Optional local-AI helpers are not admission prerequisites.

   Codex uses the installed App Server `account/rateLimits/read` method, never `codex exec`. It accepts only explicit boolean `ordinaryUsageAllowed` together with a non-empty active account identity and the expected Codex bucket. The App Server response has no backend timestamp, so the synchronous read is stamped locally with a maximum 60-second lifetime; percentages and reset estimates do not grant permission. Missing/null values, wrong identity/bucket, errors, and timeouts remain UNKNOWN.

   Antigravity capacity uses its read-only `/usage` slash command in headless print mode (`agy --output-format json -p "/usage"`). Authority comes from one controlled invocation of the configured, resolved AGY executable—not from JSON shape alone: mini me verifies the executable path/version through the existing provider capability preflight, creates a fresh private `0700` directory and log path, captures stdout/stderr, child identity, exit status, and completion time, and binds the parsed payload and authentication log to that same invocation. No pre-existing session is signaled, terminated, or modified. The adapter accepts only a successful invocation with an unambiguous authenticated account identity from the invocation's own log; the matching auth event must identify the supported `consumer` auth method. Missing, repeated with conflicting identities, malformed, or contradictory auth evidence is UNKNOWN. The raw email, log contents, credentials, and tokens are never persisted or emitted.

   The selected reviewer/implementer model identity and the provider's quota scope are distinct facts. The `/usage` result's Gemini group and bucket IDs identify a quota scope, not the selected model. The adapter must bind the configured selected AGY model to a supported model-to-group mapping; it must not infer membership by parsing descriptive prose or treating a generic group label as the model. If the installed CLI response and supported mapping do not establish that the selected model is covered by the observed quota buckets, capacity is UNKNOWN. Record the selected model and quota scope using existing normalized capacity/event evidence; do not add a parallel capacity store. Any schema extension requires a demonstrated persistence gap and an Alembic migration.

   Observation time is the controlled invocation completion time; the adapter also records the start for duration/timeout validation, rejects impossible/future timestamps, and sets expiry no later than 60 seconds after completion. It validates every required bucket reset time as a timezone-aware instant strictly later than completion. A past, malformed, or mutually contradictory reset is stale/UNKNOWN even if `remaining_fraction` is positive. A zero remaining fraction with a valid future reset is EXHAUSTED. These facts avoid races against concurrent or long-lived user sessions (such as PID 6774) without relying on their statusLine callbacks.

This executes zero agent turns, consumes zero tokens, leaves no active conversation files, and mutates zero persistent settings files (`settings.json`).

   - **Mandatory Fields & Types:**
     - `status`: `str`, mandatory, must strictly equal `"SUCCESS"`.
     - `num_turns`: `int`, mandatory, must strictly equal `0` (booleans strictly rejected). Any value > 0 indicates inferential execution and fails closed.
     - `usage`: `dict`, mandatory; `total_tokens`, `input_tokens`, and `output_tokens` must each be explicitly present as non-boolean integers equal to zero. Missing counters are not defaulted. Optional counters such as `thinking_tokens` or `cache_read_tokens`, when present, must be non-boolean integers equal to zero; malformed or non-zero values fail closed.
     - `command.name`: `str`, mandatory, must equal `"usage"`.
     - `command.data.groups`: `list[dict]`, non-empty, must contain exactly one unambiguous supported quota group for the selected model.
     - `buckets`: the selected model's verified quota scope must contain exactly one `gemini-weekly` and one `gemini-5h` bucket; duplicate conflicting IDs are rejected.
     - `remaining_fraction`: finite JSON number, mandatory for each bucket, bounded 0.0 <= f <= 1.0 (booleans strictly rejected).
     - `reset_time`: `str`, mandatory for each bucket, valid timezone-aware ISO 8601 timestamp strictly later than the observation time.
   - **Identity & Provenance:**
     - Captured only from the fresh per-invocation CLI `--log-file` via a successful auth initialization event: `applyAuthResult: email=<email>, authMethod=consumer`.
     - The invocation must use the configured resolved AGY executable, exact read-only command, private fresh log path, and successful process exit. The payload parser alone, caller-provided JSON, agent transcript, statusLine callback, or a pre-existing log cannot authorize capacity.
     - Require one normalized account identity; missing identity or conflicting successful identity events fail closed. The CLI invocation is the trusted local acquisition boundary; this is not described as cryptographic/provider-server attestation.
     - Redacted to a 64-character lowercase hex SHA-256 digest (`account_id` / `account_fingerprint`).
     - Plaintext email, credentials, and tokens are NEVER stored, emitted, or exposed in durable state or telemetry.
   - **Freshness & Lifetime (TTL):**
     - Maximum observation lifetime is bounded to 60 seconds (`timedelta(seconds=60)`).
     - An observation older than 60s, a reset time at or before observation time, or a reset time that cannot be parsed unambiguously is STALE/UNKNOWN and cannot authorize dispatch.
   - **Authenticity & Source Signal Authority:**
     - Only `CapacitySignalSource.AGY_PRINT_USAGE` produced by the registered adapter's controlled read is recognized as authoritative for dispatch admission. A structurally constructed observation or parser result without acquisition evidence is not persistence/admission authority.
     - `CapacitySignalSource.AGY_STATUSLINE` is demoted to secondary/informative telemetry only; it cannot authorize admission or dispatch and returns `False` in `record_capacity_observation`.
   - **Failure Modes & Dispatch Block Propagation:**
     - Any missing field (including `output_tokens`), unparseable payload, non-zero turns/tokens, duplicate/conflicting identity or bucket records, unsupported model-to-group mapping, out-of-bounds fraction, elapsed reset, stale timestamp, uncorroborated invocation provenance, non-zero process exit, timeout, or CLI error fails closed to `UNKNOWN` (or `EXHAUSTED` only for a valid current observation whose required quota fraction is 0.0).
     - The failure propagates to `ProviderHealthService.has_fresh_capacity_evidence("antigravity") == False`.
     - The scheduler/pipeline marks the job as `WAITING_CAPACITY` and suspends dispatch without consuming provider inference or failing the job.

   **Antigravity Capacity Invariants and StatusLine Demotion:**
   - **Fail-closed on incomplete or absent data:** Missing or incomplete fields (`num_turns`, `total_tokens`, `usage`, or quota buckets) SHALL NEVER equate to zero consumption or implicit capacity. Without positive proof of non-inferential execution (`num_turns: 0` and verified token metrics) and complete valid quota buckets, the observation strictly fails closed as UNKNOWN.
   - **Demotion of statusLine telemetry:** Under this R01 contract, Antigravity `statusLine` telemetry is not an authoritative capacity source and cannot authorize scheduler admission or stage dispatch. It may be retained only as secondary/informative telemetry; it cannot be promoted based solely on plausible fields, `session_id`, or a claimed callback identity.
   - **Mandatory 5-vector regression suite:** Deterministic capacity verification MUST cover:
     1. `incomplete_payload`: independently omit `num_turns`, `usage`, each required token counter (including `output_tokens`), each quota bucket, fraction, and reset; none defaults to zero and each yields UNKNOWN.
     2. `forged_or_contradictory_payload`: positive turns/tokens, booleans, malformed types, non-zero optional counters, duplicate conflicting group/bucket IDs, and conflicting reset/fraction evidence fail closed.
     3. `stale_payload`: observation TTL elapsed, future observation timestamp, expired/equal reset, or reset inconsistent with the captured invocation blocks dispatch.
     4. `unknown_provenance`: direct parser JSON, caller-created observations, missing/multiple conflicting auth events, wrong auth method/account, stale log, wrong executable, non-zero exit, timeout, and standalone statusLine signals cannot authorize persistence or admission.
     5. `identity_and_scope_mismatch`: wrong account, unsupported selected model, or quota group/bucket not mapped to that model produces UNKNOWN.
     6. `acquisition_to_dispatch`: only the adapter's actual controlled read can be persisted through the existing health authority; UNKNOWN/EXHAUSTED at persistence or the final JIT dispatch check prevents invocation and preserves work.
     7. `valid_signal`: controlled successful non-inferential `/usage`, unambiguous authenticated identity, explicitly zero required counters, supported selected-model/quota-scope mapping, and positive current remaining fractions produces AVAILABLE.

   Historical validation on 2026-10-14 observed the installed AGY 1.3.5 `/usage` command report zero turns/tokens and positive Gemini bucket fractions. This records a historical observation only; it does not by itself prove the current executable, account, selected-model mapping, freshness, persistence path, or current dispatch eligibility. Each admission/APPLY/REVIEW stage must obtain and validate its own current observation.

3. **Evidence requires independent observation.** Reuse existing attempt, event, candidate-manifest, check, review, and external-action persistence where it provides the required evidence. Persist only demonstrated gaps through existing PostgreSQL repositories and use Alembic if a schema addition is necessary. Corroborate native workflow use with process/tool traces plus artifact/diff and candidate observations; transcript assertions alone are insufficient. Bind check/review/PR evidence to exact candidate SHA, base SHA, generation and repository identity. Unknown external outcomes are observed/reconciled before retry.

**Candidate worktree lifecycle:** candidate-free attempts keep the existing snapshot-then-cleanup/recreation authority unchanged. Once an active Run/Job has a candidate SHA and candidate manifest, the execution pipeline retains its already-owned physical worktree through candidate review/remediation instead of transitioning ownership to `DELETED`. Re-entry is a separate read-only adoption proof: exactly one current frozen candidate must bind the active Run and Job, generation, original base, candidate ref/SHA and manifest; ownership must be `CREATED`, the path/marker/Git registration/repository binding must match, HEAD and branch ref must equal the frozen candidate, the tree must be clean and its recomputed manifest must match. Candidate evidence never enters `_verify_deleted_worktree_recreation()`. Missing/deleted ownership or any contradictory/dirty evidence fails closed and leaves existing state untouched; it is not reconstructed from the current base.

**Generated compiler and runtime artifact exclusion policy:**
- **Strict exclusion from manifest and commits:** `CandidateManifestService` and candidate preparation enforce zero tracking of generated bytecode or cache files (`__pycache__`, `*.pyc`, `*.pyo`, `.pytest_cache`, `.coverage`, etc.). Any candidate attempt that attempts to commit or stage these artifacts is rejected during manifest generation, failing closed before checks or review.
- **Check runner isolation:** `ChecksRunner` and test execution environments must isolate bytecode caching (e.g. by setting `PYTHONPYCACHEPREFIX` to an isolated ephemeral directory outside the worktree, or enforcing explicit exclusion rules). Tests executed inside candidate worktrees must not leave uncommitted `.pyc` files or cache directories behind.
- **Post-check worktree hygiene:** Immediately after check execution, worktree status is validated. If transient runtime artifacts are detected, the runner fails closed unless a sanitized remediation restores pristine worktree state matching the candidate manifest.
- **Non-destructive remediation of frozen candidates:** When an existing frozen candidate worktree contains transient, untracked runtime artifacts (e.g., from local test runner execution), remediation purges the transient files using non-destructive cleanup (`git clean -fdX` or explicit removal of transient directories) without rebasing, resetting candidate commits, mutating the frozen candidate SHA, or discarding historical attempt/event records. Re-entry verification then confirms the clean worktree matches the frozen manifest hash byte-for-byte.

4. **DeepSeek review stages are separate and independently evidenced.** CONTRACT REVIEW is a pre-APPLY, read-only review of the exact OpenSpec contract. Code REVIEW is a distinct read-only review of the exact frozen candidate, bound to repository/base/head/generation/manifest and independent of all surviving substantive authors. Each has its own input, reviewer-stage identity, structured result, usage record, and durable evidence; neither can be reused for the other. DeepSeek Direct uses only its own official API/account and requires verified compatibility, account identity, fresh capacity/balance, and compliance with the owner's configured spending policy before a call. Ordinary calls do not require a new human approval or mandatory per-call maximum. If a required review cannot run, preserve the work and wait; no silent reviewer substitution. Review findings cannot authorize APPLY, product decisions, or merge. The existing `DeepSeekAuditorRunner` and audit records are not review authority. Human merge remains mandatory.

5. **PR delivery reuses the existing durable GitHub path and stops at the human gate.** Reconcile the candidate branch and Draft PR through existing action reservation/observation semantics; the remote PR head must equal the audited/otherwise authorized current candidate SHA and reference the exact Issue and change. Human merge remains mandatory. No archive, automatic merge, production deploy, or closure is folded into this implementation stage.

6. **Fixture is the product acceptance boundary; N01 is a protected invariant.** Use one small explicitly authorized disposable GitHub repository with a real failing behavior test and an already READY change whose specs were authored through the agent-side OpenSpec proposal workflow. Run one bounded authorized real implementation, deterministic checks, separate contract and code reviews by DeepSeek Direct, and a real Draft PR. Record separate TECHNICAL_PASS, E2E_PASS and DEPLOYED_VERIFIED evidence. If inference, reviewer capacity, credentials, applicable spending policy, or deployment authorization is absent, report the relevant stage NOT_VERIFIED/WAITING and do not claim complete delivery. Capture N01 read-only identity/evidence before and after; never dispatch N01 or modify its records/worktree.

7. **Removal is proof-gated and same-change.** Inventory current prompt builders, callers, runner profiles, fixtures, tests, configuration, and dynamically selected paths. Classify every affected behavior REUSE/MODIFY/REPLACE/REMOVE/RETAIN-WITH-REASON. Retire only reachable code-authoring prompt paths that the native workflow has replaced, after a real E2E proves parity. Migrate callers and valuable tests/docs, then rerun focused checks, E2E, security denials and interruption recovery after removal. Retain `OpenSpecTaskTracker`, OpenSpec validation, deterministic orchestration and other code with justified consumers; do not remove semantic proposal generation from `OpenSpecGenerator`/intake (R02) or sync/archive behavior (R04).

### Verified R01 code/consumer census and Removal Ledger

This is the planning baseline from the current repository census, not a blanket deletion order. Every removal remains conditional on call-graph proof, replacement parity, migrated consumers, and post-removal E2E in this same Change.

#### Exact current entry points and consumers

- `ExecutionPipelineService.execute_queued_job` resolves an APPLY `ResolvedStageProfile`, checks the configured provider/model/effort, refreshes capacity for the selected model, and passes provider/model/effort to `runner_for_implementer`. The implementation still contains a `TypeError` compatibility fallback that calls the runner factory without model/effort; that fallback is an unresolved fail-open path, not evidence of exact profile dispatch. REVIEW similarly resolves and passes a stage profile to `runner_for_reviewer`, but has the same fallback pattern. These entrypoints require tests proving that a profile-construction error blocks dispatch and cannot silently select another invocation.
- `format_candidate_workspace_context` supplies the worktree boundary. Retain and keep it in the native workflow request; the path is corroborative context, never repository authority.
