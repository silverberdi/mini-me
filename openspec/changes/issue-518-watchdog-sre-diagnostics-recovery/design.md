## Context

See `proposal.md` for the motivation and `specs/` for observable behavior. The repo already has a subprocess-level `ProgressWatchdog`, the periodic `scheduler_run_cmd` loop with PostgreSQL wake-up hints, `RunRecoveryService`, and `NativeOrchestrationCoordinator`, which dispatches work through existing run claims, stage-invocation evidence, and fencing checks. Those existing mechanisms are the boundaries for observation and mutation. There is no separate `RecoveryConvergenceService`, global Watchdog configuration, or persisted cross-project diagnosis/feed model in this checkout.

## Goals / Non-Goals

**Goals:**
- Observe stalled active runs through existing scheduler reconciliation with no model call or lifecycle change while activity is current.
- Store the smallest durable global settings and per-run evidence needed for safe decisions, operator display, and suggestion handling.
- Keep destructive recovery bound to a verified managed worktree, immutable candidate, proven process state, and the canonical current fence.
- Preserve real, explainable autonomy and machine-time measurements.

**Non-Goals:**
- Add a scheduler, pipeline stage, recovery authority, generic rules engine, autonomous Issue creation, provider-specific permanent role, or deployment behavior.
- Treat an inactivity signal as proof that a process is dead or that cleanup is safe.

## Decisions

1. **Observe from existing reconciliation; keep activity checks cheap.** Add a Watchdog evaluation hook to the current periodic/reconciliation path, using persisted stage events and available activity/process evidence. Healthy activity exits before semantic diagnosis or model invocation. This reuses the existing scheduler and its wake-up fallback; a separate timer/service loop would add another authority and drift risk.

2. **Use one global settings record and candidate-bound diagnosis records.** Add the minimum PostgreSQL persistence: a singleton global configuration for model selection, threshold, and mode; and one durable diagnosis record per run/stage/candidate, carrying sanitized evidence, cause, action/result, and an optional improvement draft/status. The global selector reuses the existing administration registry for enabled/available catalog models and the existing global agent catalog for currently stage-selectable Codex and Antigravity models. It is not scoped to a focused project's profiles. The API validates against the same union before saving; it does not accept arbitrary provider/model strings. The optional suggestion stays with its source diagnosis rather than creating a parallel feed lifecycle. Do not store credentials or duplicate project/provider state.

3. **Keep model reasoning advisory; deterministic proof controls action.** Invoke the configured model only after a stall is observed and use it to classify evidence and draft an operator-readable suggestion. A model response never authorizes a mutation. The deterministic playbook decides whether a known safe condition is proven; unavailable model capacity does not block such a playbook, and unclassified cases escalate through the existing human gate. Do not silently switch provider or exceed configured spend authority.

4. **Route every repair through the existing orchestration path.** Have the current scheduler loop pass detected Watchdog work to `NativeOrchestrationCoordinator` and its persisted run/stage claim and recovery checks. The Watchdog itself remains an observer/planner and cannot directly change run state, claims, candidate identity, or dispatch. Existing claim, fencing, idempotency, gate, and worktree-ownership rules remain authoritative; there is one remediation attempt for a run/stage/candidate before escalation. Creating another convergence service was rejected because it would duplicate the existing coordinator path and recovery authority.

5. **Narrow worktree cleanup to proven Verify outputs.** The Issue's `git checkout -- .` is unsafe because it can erase unrelated tracked changes and test evidence. Restore only when the exact owned worktree and candidate match, the Verify process is proven absent, and every changed path is tied to the recorded baseline and generated by that invocation. Preserve evidence and fail closed for any unknown path, process, or ownership. Reuse existing managed-worktree cleanup/lock recovery rather than introducing a general cleanup engine.

6. **Make autonomy an observed completion ratio.** The Issue explicitly asks for the share of completed runs that needed no operator action. Compute each time bucket from completed runs with complete intervention evidence; successful Watchdog-only recovery counts as autonomous, while any required operator response counts as operator-assisted. Exclude incomplete, failed, cancelled, or ambiguous runs, and show no-data for an empty denominator. Keep technical retry/loop observations separate from this rate, replacing the incompatible continuous per-run autonomy interpretation in the existing spec.

7. **Keep suggestion handling operator-owned.** The feed reads persisted diagnosis suggestions and supports copy-as-draft and discard. `Convertida` means the draft was copied successfully; it does not mean a GitHub Issue was created. No GitHub write is added.

## Risks / Trade-offs

- [Incorrect stall classification could trigger needless intervention] → Require threshold expiry plus durable event/activity evidence; a stall signal alone never proves process absence or grants cleanup.
- [Automatic cleanup could destroy candidate or test evidence] → Restrict it to exact owned worktrees, immutable candidate identity, proven-absent Verify process, attributed generated paths, and the existing fenced cleanup authority; otherwise preserve and escalate.
- [Changing the autonomy chart semantics can alter historical interpretation] → Use only verifiable completed-run intervention evidence, leave unsupported historical buckets as no-data, and label the dimension as the observed completion share.
- [A global role may be unavailable or invalid] → Validate against the existing catalog, preserve last valid settings, and allow only deterministic safe playbooks when the semantic model is unavailable.
- [Persisted diagnostics may contain secrets or unrelated project data] → Apply existing dashboard sanitization and project authorization before storage/projection; never include credentials or unsanitized provider output.

## Migration Plan

1. Add a conservative Alembic migration for the singleton Watchdog configuration and candidate-bound diagnosis records, including the optional improvement draft and its status. Seed defaults only if no settings row exists: 15 minutes and `Solo diagnóstico`; leave provider/model unselected until an operator selects an available catalog entry.
2. Deploy code that can read absent settings as these defaults and preserves existing telemetry data. Do not delete or reinterpret old per-run autonomy data; historical buckets without complete intervention evidence return no-data under the new definition.
3. Rollback by disabling Watchdog evaluation and reverting code. Keep persisted diagnosis/configuration rows intact for forward recovery; schema downgrade must not be required for application rollback.
