# PWA API and view authority map

Captured from `app.openapi()` and Pydantic response models on the isolated Change worktree at `7df73fe3f556cc47e58e002226247eba8f37e5a6` plus the local read-model delta. This is a static contract inventory, not proof of runtime freshness or browser behavior. OpenAPI emitted pre-existing duplicate operation-ID warnings for `/health`, `/`, and `/dashboard`.

| Surface | Authoritative read/write contract | Confirmed fields used or available | Client behavior / limits |
|---|---|---|---|
| API and PostgreSQL health | `GET /health` | `status`, `database.engine`, `database.healthy`, `database.message`, `version` | Header uses only `database.healthy`; it does not infer scheduler state. Requests use same-origin credentials and `cache: no-store`. |
| Overview / attention / active work | `GET /api/v1/dashboard/overview` → `DashboardOverviewResponse` | `system_status`, `attention_items`, `active_executions`, `recent_completions`, `changes`; system fields include logical `scheduler_mode`, health and server counts including active, attention, queue, total changes and recent completions; attention and execution fields carry project/change/Run/Job/stage/reason/candidate identity | Existing dashboard renderer consumes server-owned counters. Missing panel response shows unavailable/UNKNOWN rather than zero. `scheduler_mode` is explicitly labelled logical admission. |
| systemd scheduler observation | Embedded `system_status.scheduler_service` → `SchedulerServiceStatusDTO` | `active_state`, `sub_state`, `enabled_state`, `source`, `observed_at`, `age_seconds`, `freshness`, `reason` | UI shows service activity and boot enablement independently; non-FRESH is rendered UNKNOWN. Observation is backend-only and restricted to the fixed unit. |
| Queue and explanation | `GET /api/v1/queue`; `GET /api/v1/queue/{change_name}/explain?project_id=…` | `WorkQueueItem`: project/change, Issue title/number, priority, roadmap stage, dependencies, `readiness_state`, unmet reasons, `blocked_reason`, server `admission_eligible`, server `priority_score`, discovered/evaluated times | Queue component displays supplied readiness, eligibility, priority and reasons. It does not rank, calculate readiness, or infer capacity. |
| Provider health | `GET /providers/health` | `provider`, `model`, `status`, `last_probe_at`, provider-health history fields | Component displays provider/model/status/observation only. It does not present invented latency, quota or spend. |
| Scheduler logical mode | `GET /api/v1/scheduler/status` and `/scheduler/status` → `SchedulerStatus` | `mode`, `admission_allowed`, `active_jobs_count`, `primary_capacity_available`, `reason`, `recovery_state`, `updated_at` | Logical admission remains distinct from systemd. Service observation never controls scheduler. |
| Run list and detail | `GET /api/v1/orchestration/runs`; `GET /api/v1/dashboard/runs/{run_id}`; `GET /api/v1/dashboard/changes/{project_id}/{change_name}?run_id=…` | Durable `OrchestrationRun`: Run/project/change/base SHA/stage/resumable stage/outcome/gate/reason/Job/generation/candidate/retry/handoff/active and timestamps. Detail response: project/change/status/Run/Job/stage/branch/executor/stop/human gate, pipeline, candidate authority/history, checks, review, audit, GitHub, preview validation, timeline and blockers. Added `repository_identity`/`repository_binding_state` from the exact `ProjectBinding` row for the project/change. | `repository_identity` is returned only for a present `is_valid` binding with no mismatch reasons and non-empty repository; INVALID/UNKNOWN states suppress the raw repository string. Existing `renderDetail` displays the returned value and status without a client-side repository lookup. SHA and generation are not joined client-side across Runs. |
| Events / activity | `GET /api/v1/dashboard/events` → `TimelineEventDTO[]` | `event_id`, `timestamp`, `event_type`, `from_stage`, `to_stage`, `actor`, `summary`, redacted `details` | Rendered as recorded events; no client-created execution history. |
| Efficiency / budget | `GET /api/v1/efficiency/{project_id}` → `ProviderEfficiencyMetrics`; `/{project_id}/{change_name}` → `EfficiencyTelemetryView`; `GET /budget/usage` (untyped JSON dict) | Efficiency metrics include provider attempt/duration/productivity/retry/reassignment/exhaustion/drain/premium/candidate-generation and stage/cycle timing counters. Telemetry view contains `project_id`, `change_name`, `run_id`, `metrics`, `provider_summary`, `evaluated_at`. Budget response contains `project_id`, `policy`, `headroom`, unresolved settlement count/USD, reservations, ledger and `token_usage_by_model` (no Pydantic response schema is declared). | Display only server-returned values where present; no client-side cost estimate. Untyped budget route remains an API typing limitation and is not treated as permission to infer. |
| Actions | `GET /api/v1/control-plane/actions/available?run_id=…` → `ActionDescriptor[]`; `POST /api/v1/control-plane/actions/execute` → `OperatorActionResult` | Descriptor: action/display/description/enabled/disabled reason/confirmation/risk/parameter schema. Result: action request id/type/status/error/summary/result stage/outcome/gate/evidence/payload/executed time/success. | UI uses only discovered actions and confirmation/result path. No merge action or direct command/Git/systemd/provider path is introduced. |
| Preview and human validation | `GET /api/v1/previews/{preview_id}` (dict JSON); `GET /api/v1/validations/authority/{project_id}/{change_name}` (dict JSON); scenarios and submit endpoints | Preview dict carries preview/project/change/Run/generation/head/base/image identity/status/URL/port/container/failure/timestamps. Authority dict carries `is_preview_required`, `is_authorized`, `is_stale`, latest validation id/verdict. Scenario/validation domain models are mapped by existing detail DTO. | Existing preview/validation views retained; candidate identity and stale result gates remain backend-authoritative. These dict-returning routes have no generated typed response schemas. |
| Authentication | `GET /api/v1/auth/me` → `AuthStatusDTO`; logout route used by current controller | `authenticated`, `operator`, `session_expires_at` | Identity is displayed only while authenticated. Operational reads are same-origin and non-cacheable; 401 clears the visible operational model and returns to login. |

## Unresolved field gaps

- Real runtime contract coverage for every optional detail tab, budget/efficiency widget and action response remains open; no field should be added to the UI until confirmed by Pydantic/OpenAPI and its consumer.
- Browser-level auth expiry, logout/login isolation and stale-panel behavior are tested separately in `test_pwa_real_browser.py`; this static map does not replace those runtime checks.
- On this macOS host, the system D-Bus cannot prove a real scheduler observation. The backend intentionally returns UNKNOWN when the supported read-only D-Bus source is unavailable.
- API health can be read independently, but neither health nor PostgreSQL status supplies a freshness timestamp; the UI labels its local receipt time as receipt time, not source observation time.
