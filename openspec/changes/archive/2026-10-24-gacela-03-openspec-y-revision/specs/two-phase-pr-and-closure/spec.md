## Purpose
Manage the two-phase pull request delivery cycle, complexity-differentiated merge policies, fresh documentation worktree setup, native OpenSpec Sync and Archive execution, second PR auto-merge, remote issue closure, and continuous transition to the next eligible Request.

## ADDED Requirements

### Requirement: Implementation Pull Request Preparation via Minimal Skill Delivered in F3
The system SHALL deliver the minimal PR preparation skill (`minime-pr-preparer`) within F3 and SHALL invoke it to generate the structured title and Markdown description for the implementation PR without depending on F4 capabilities. The skill contract SHALL accept structured input (project, repository, `pr_type: implementation`, original request details, base branch, candidate branch, candidate commit SHA, change summary, test/verify evidence, and OpenSpec change name) and SHALL return structured output (formatted title, structured description with test evidence, informative issue reference such as `Ref #...` or `Addresses #...`, and metadata, strictly excluding auto-closing keywords like `Fixes`, `Closes`, or `Resolves` to prevent premature issue closure). The system SHALL use `GitHubAdapter` to push the branch, open the Pull Request, bind it to the verified candidate SHA, and check remote protections. Agent guardian directives (`minime-git-workspace-guardian`, `minime-github-work-management-guardian`) SHALL apply strictly to autonomous agent git operations in the worktree, whereas the remote merge SHALL be executed exclusively by mini me coordinator via `GitHubAdapter`.

#### Scenario: Implementation PR prepared via minimal skill and opened
- **GIVEN** verified implementation with all unit and E2E tests passing (exit code 0)
- **AND** independent code review approved (or skipped for low/moderate complexity)
- **WHEN** mini me dispatches `minime-pr-preparer` via `CliAgentRunner` with change summary and test logs
- **THEN** the skill returns structured PR title, body, and informative references
- **AND** `GitHubAdapter.create_pull_request` opens PR1 on GitHub bound to candidate SHA
- **AND** the PR URL and number are stored in PostgreSQL.

#### Scenario: PR preparation strictly excludes auto-closing keywords
- **GIVEN** PR content generated by `minime-pr-preparer` for PR1 or PR2
- **WHEN** the PR body is inspected prior to submission
- **THEN** it contains non-closing references (e.g. `Ref #...` or `Addresses #...`)
- **AND** contains no closing keywords (`Fixes`, `Closes`, `Resolves`)
- **AND** merging PR1 does NOT close the remote GitHub Issue.

### Requirement: Merge Policy for Implementation PR
The system SHALL apply a differentiated merge policy for the implementation PR based on the complexity assessed during Propose: for low or moderate complexity, mini me SHALL merge the PR automatically; for high complexity, mini me SHALL emit `HUMAN REQUIRED` exclusively for an informational acknowledgement («Estoy enterado») with a plain Spanish summary before merging.

#### Scenario: Low or moderate complexity PR merges automatically
- **GIVEN** PR1 opened on GitHub for low or moderate complexity change
- **AND** all remote CI checks, reviews, and branch protections satisfied
- **WHEN** mini me coordinator invokes `GitHubAdapter.merge_pull_request`
- **THEN** GitHub executes the merge into `main` returning merge commit SHA
- **AND** mini me records the merge SHA and advances stage to fresh documentation worktree setup.

#### Scenario: High complexity PR requires human informational acknowledgement
- **GIVEN** PR1 opened on GitHub for a high complexity change
- **WHEN** the change reaches merge stage
- **THEN** mini me emits `HUMAN REQUIRED` status with concise Spanish summary of changes and test evidence
- **AND** pauses execution without merging
- **AND** upon operator submitting «Estoy enterado», executes `GitHubAdapter.merge_pull_request` immediately.

#### Scenario: Remote branch protections are strictly respected
- **GIVEN** an automated or acknowledged merge attempt on GitHub
- **WHEN** required reviews, checks, or status contexts are missing or failing
- **THEN** `GitHubAdapter.merge_pull_request` raises a typed merge error
- **AND** mini me halts fail-closed, preserving PR state and worktree without attempting unauthorized overrides.

### Requirement: Fresh Worktree Setup for Documentation Closure
Following remote confirmation that the implementation PR is merged into `main`, the system SHALL update the remote reference of `main`, SHALL create a fresh documentation branch (`doc-close-<numero>-<slug-kebab>`) and worktree rooted at the merged `main` commit under the project's configured managed root, and SHALL NOT reuse the dirty implementation worktree.

#### Scenario: Documentation branch and worktree rooted on merged main
- **GIVEN** confirmed merge commit SHA of PR1 on remote `origin/main`
- **WHEN** mini me prepares for documentation closure
- **THEN** `WorktreeManager` fetches updated `origin/main`
- **AND** creates fresh branch `doc-close-<numero>-<slug-kebab>` pointing to the PR1 merge commit
- **AND** provisions an isolated worktree under `.minime/worktrees/` containing the clean repository state.

### Requirement: Native OpenSpec Sync and Archive Execution
The system SHALL dynamically resolve the official OpenSpec Sync and Archive workflows for the thinking agent based on the workflows installed in the documentation worktree (`.agent/workflows/opsx-sync.md` and `opsx-archive.md` for Antigravity vs `.agents/skills/openspec-sync-specs/SKILL.md` and `openspec-archive-change/SKILL.md` for Codex) and provider prompt transport. The system SHALL dispatch the thinking agent configured with lowest compatible effort to execute the resolved Sync workflow followed by Archive, SHALL commit and push the resulting documentation changes, and SHALL NOT emulate Sync or Archive via custom Markdown scripts or manual directory moves (`shutil.move`).

#### Scenario: Thinking agent executes native sync and archive
- **GIVEN** the fresh documentation worktree rooted on merged `main`
- **AND** verified presence of native Sync and Archive workflows for the thinking agent
- **WHEN** mini me dispatches the thinking agent with lowest effort to execute native Sync then native Archive
- **THEN** main specs in `openspec/specs/` are updated with the delta specs
- **AND** change folder is archived under `openspec/archive/`
- **AND** the changes are committed and pushed to `doc-close-<numero>-<slug-kebab>` without Python file-moving scripts.

#### Scenario: Emulation avoidance verification
- **GIVEN** execution of documentation closure stage
- **WHEN** mini me coordinates sync and archive
- **THEN** no Python filesystem operations (such as `shutil.move` or regex spec mergers) touch `openspec/`
- **AND** all modifications originate from the native agent runner invocation.

### Requirement: Documentation Pull Request via Minimal Skill and Auto-Merge
The system SHALL invoke the minimal PR preparation skill (`minime-pr-preparer`) with `pr_type: documentation` for the documentation branch, SHALL open a second Pull Request from the documentation branch to `main` via `GitHubAdapter`, SHALL verify that it contains exclusively documentation and OpenSpec updates, and SHALL automatically merge it regardless of the original change's complexity.

#### Scenario: Second PR auto-merges unconditionally
- **GIVEN** documentation branch pushed to remote with native Sync and Archive commits
- **WHEN** mini me invokes `minime-pr-preparer` for documentation PR
- **AND** opens PR2 via `GitHubAdapter`
- **THEN** mini me automatically merges PR2 into `main` without requiring human acknowledgement
- **AND** confirms the second merge commit SHA from GitHub.

### Requirement: Remote Issue Closure, FIFO Continuation, and Test Isolation
Only after remote confirmation that the second documentation PR is merged into `main`, the system SHALL close the remote GitHub Issue, record idempotent completion in PostgreSQL, release the active project lock, and immediately invoke request selection for the next eligible FIFO Request. All E2E automated tests exercising PR creation, merge, and issue closure SHALL execute exclusively against an authorized, isolated test repository without mutating the operational mini me repository or issues.

#### Scenario: Remote issue closed and next ticket selected
- **GIVEN** PR2 successfully merged into remote `main`
- **WHEN** mini me coordinator detects the PR2 merge confirmation
- **THEN** `GitHubAdapter.close_issue` marks the GitHub issue as closed with completion comment
- **AND** the PostgreSQL run record is updated to completed
- **AND** the project active lock is released
- **AND** intake selects the next oldest open eligible GitHub issue in FIFO order.

#### Scenario: End-to-end pull request and closure tests run in isolated repository
- **GIVEN** automated E2E test execution for PR creation, merging, and issue closure
- **WHEN** the test suite executes
- **THEN** all remote operations target an authorized fixture repository (e.g. `mini-me-fixture`)
- **AND** zero operations mutate `silverberdi/mini-me` or production issues.
