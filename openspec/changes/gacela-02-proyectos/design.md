## Context

La propuesta cubre la entrega íntegra de F2 definida en Issue #170. La base inspeccionada es `origin/main` en `2f7ae04` (merge de F1 documental); el Change F1 permanece archivado en `openspec/changes/archive/2026-10-22-gacela-01-depuracion-inicial/`. El head Alembic actual es `gacela01_retire_legacy_admission_state`; no se ejecutó migración ni se consultó/escribió una base operativa durante Propose.

El estado actual incumple el resultado: `ProjectService` persiste roles `implementer/reviewer` con regla fija Codex/Antigravity y configura políticas heredadas; `ProjectOnboardingService` implementa un segundo alta basado en GitHub App, workspace y descubrimiento local, con identidad más inmutable que la configuración; `POST /projects` y `POST /api/v1/projects/onboard` difieren en validación y efectos; `Project`/`projects` contienen backlog/roadmap/contexto local y campos de admisión; GitHub agrupa Tickets y Git/PR; `native_openspec_apply.py` solo resuelve Apply. F1 dejó OpenSpec y estado legacy retirados, no un proceso de bootstrap de proyectos.

Spec reconciliation: F2 modifica únicamente la canónica equivalente `openspec/specs/project-registry/spec.md` y agrega contratos que aún no existen. `autonomous-intake-preparation-and-admission` and `autonomous-work-discovery` still contain local-backlog/admission behavior that conflicts with F1's `legacy-admission-and-state-retirement` delta and the rector; they are historical conflict evidence, not executable authorization, and F2 will neither revive nor rewrite their F3 ticket-selection behaviors. `github-work-binding`, `repository-binding`, and `managed-repository-runtime-isolation` remain useful identity/PR/workspace contracts; F2 preserves their guarantees and only supplies project onboarding use. No historical Change is edited, archived, or executed by this proposal.

Restricciones: una API FastAPI y PostgreSQL/Alembic; GitHub es el único adaptador funcional en F2; agentes ejecutan archivos y workflows nativos; tickets remotos son autoridad y F3 implementa su ciclo; ningún secreto se serializa en configuración, logs, prompts o repositorio; no hay UI F2, scheduler, auto-merge, ADO ni ejecución brownfield.

## Goals / Non-Goals

**Diseño logra:** una sola configuración durable por proyecto, roles desacoplados de proveedor, un flujo greenfield recuperable hasta PR y confirmación de merge, configuración brownfield explícitamente no preparada, y contexto incremental aprobado por PR.

**No logra:** selección/ejecución autónoma de Issues; workflow OpenSpec propio; gestión universal de secretos/proveedores; adaptador ADO; UI; migración brownfield; auto-merge de PR; despliegue; skills de interacción externa reservadas a F4.

## Decisions

### 1. Un único registro de proyecto y dos contratos GitHub

`ProjectService` conserva invariantes de identidad y transacción; `ProjectOnboardingService` se convierte en único coordinador de alta/recuperación. API y CLI llaman el mismo servicio. Dentro de una configuración de proyecto se guardan por separado `ticket_source` y `git_provider`; comparten proveedor de catálogo `github` y pueden señalar repos distintos. Contratos de interfaz pequeños: TicketSource ofrece list/read/create/comment/close según contrato, Git/PR ofrece repo/branch/worktree/commit/push/PR/merge observation. F2 implementa credenciales/validación y operaciones requeridas por bootstrap/context PR; selección y ciclo de Issues queda diferido a F3. No crear framework/plugin loader.

Alternativa rechazada: una sola interfaz GitHub con llamadas ambiguas o campos de conexión globales; mezcla autoridad de ticket y repo y filtraría credenciales/global scope entre proyectos.

### 2. Catálogos son capabilities, configuración es dato de proyecto

Registro estático mínimo respaldado por adaptadores ejecutables declara id, responsabilidad (`tickets` o `git_pr`), capacidades, campos requeridos, método de autenticación y estado real (`available`/`unavailable`). No contiene host/org/repo ni secret. Para agentes se toma configuración/CLI instalado más descubrimiento verificable de modelos, esfuerzo, transporte de prompt, acceso a archivos, rol admisible y skills/workflows hallados en el workspace. UI futura consumirá este catálogo; F2 expone API/CLI.

Project almacena proveedor+conexión por separado y 4 perfiles nombrados `thinking`, `execution`, `independent_review`, `fallback`: executor id, model id, effort, etapas/workflows nativos comprobados, skills referenciadas y estado de selección. No guarda comandos libres; el resolver compone la invocación desde `resolve_cli_invocation` y presencia real de workflow/skill. El catálogo comprueba la versión efectiva de OpenSpec y las capacidades oficiales disponibles; cada agente seleccionado recibe/configura el conjunto completo de comandos, skills y workflows oficiales compatibles con esa versión, incluidas operaciones extendidas, no solo las necesarias en su perfil inmediato. Los perfiles determinan qué operaciones se despachan, no reducen el conjunto instalado. Cada rol debe ser ejecutable para su función; fallback además necesita autorización y gasto permitido. El esfuerzo por defecto es medio para propose/apply/verify/review y el mínimo compatible para sync/archive. La revisión de propuesta en F3 es siempre obligatoria; la revisión de código es condicional según la política sencilla del proyecto; el revisor nunca es autor del candidato. F2 valida/persiste perfiles y usa pensamiento una sola clase de tarea: organizar el ZIP; F3 conecta el flujo de ticket.

Alternativa rechazada: convertir `native_openspec_apply` en workflow router / state machine. Se extrae solo resolución verificable de workflow nativo por agente y se conserva el dispatcher Apply ya probado para su consumidor legítimo.

### 3. Credenciales GitHub por proyecto sin aprovisionamiento manual

La implementación presente usa GitHub App installation: `GitHubAppAuth` necesita app id, installation id y ruta a clave privada fuera del repo. F2 permite exactamente dos modalidades por conexión: (a) credencial de mini me vía `.env`, solo cuando se elige expresamente; (b) GitHub App propia del proyecto. En create/edit autenticado, el operador aporta `app_id`, `installation_id` y clave privada mediante el DTO protegido por TLS o el prompt oculto de CLI (nunca argumentos visibles). Tras validar autorización y formato, el servicio escribe la clave en el root de secretos configurado por el host, usando nombre opaco generado por el servidor, archivo regular con permisos restrictivos y escritura atómica; persiste en el proyecto solo modo, IDs no secretos y una referencia opaca ligada al proyecto. La referencia nunca acepta una ruta del cliente ni permite traversal/symlink. El host controla root, propietario y permisos; si no puede garantizarlos, la operación falla cerrada. No se exige copiar archivos manualmente por SSH.

La respuesta de API/CLI solo expone modo y estado no sensible. No se devuelve ni registra la clave, referencia de filesystem o token; la clave no entra en PostgreSQL, Git, ZIP, prompts, entorno del agente ni PR. Los tokens de instalación permanecen efímeros. Una edición valida la nueva credencial primero y luego reemplaza atómicamente solo el secreto del proyecto; un fallo conserva la credencial previa. Operaciones de proyecto usan solo su auth bundle y una credencial propia inválida nunca cae a `.env`. Tickets y Git/PR pueden tener referencias separadas aunque ambas instancien GitHub. No aceptar PAT.

Alternativa rechazada: vault universal, catálogo de conexiones compartidas, archivo proporcionado por ruta/SSH por el operador, o nuevo formato de credenciales no soportado. La única reutilización multi-proyecto es la selección explícita de `.env` actual.

### 4. Modelo durable pequeño, estados verdaderos

La rama principal es opcional en create/edit y se normaliza a `main` cuando se omite; una rama proporcionada se valida igual que cualquier identidad remota y, si falta remotamente, sigue el procedimiento bootstrap definido.

Usar fila `projects` como autoridad única de configuración. Añadir `project_type VARCHAR`, `provider_connections JSON`, `agent_profiles JSON`, `execution_policy JSON` y `onboarding_checkpoint JSON`; mantener identidad, repo, branch y `openspec_path` existentes. `provider_connections` tiene exactamente dos claves (`ticket_source`, `git_pr`), cada una con `provider_id`, URL, repository, branch (si corresponde), `auth_mode`, credential reference e IDs no secretos del App. `agent_profiles` tiene exactamente las claves `thinking`, `execution`, `independent_review`, `fallback`, cada una con executor/provider, model, effort, role-compatible stage/workflow IDs y references to installed skills. `execution_policy` solo contiene finite correction/retry limit, proposal/code-review policy, paid-fallback authorization and project budget reference/caps already supported. `onboarding_checkpoint` stores operation revision, source ZIP hashes/provenance references, branch, base/head SHAs, PR id/url, expected base and merge observation; not file contents, ticket records, history stream or arbitrary events. Do not add provider/role/ticket/PR-history tables. If the existing project status field is the lifecycle authority, extend it with `PAUSED` while preserving legacy `ARCHIVED` as non-activatable; do not add a second lifecycle column. `onboarding_status` remains a separate truthful progress axis.

Estados mínimos distintos: `onboarding_status` = `CONFIGURED` (incluye Brownfield), `BOOTSTRAPPING`, `PR_PENDING`, `PREPARED`, `BLOCKED`; ciclo `status` = `ACTIVE`/`PAUSED` (legacy `ARCHIVED` se conserva como no activable). Mapear filas legacy `DISABLED` a `PAUSED`; `READY_FOR_WORK` sin prueba de merge no se convierte en `PREPARED`: mapear a `CONFIGURED` si identidad/proyecto es legible o `BLOCKED` si faltan perfiles/identidad. Brownfield termina `CONFIGURED`, no `PREPARED`; Greenfield está `PREPARED` solo tras PR merged verificado. Registro sin ZIP nunca crea fila Greenfield. Activar Brownfield no habilita adaptación/trabajo de F3.

Alternativa rechazada: granularizar fases de cada ZIP como una saga nueva o tener tablas por capability/role sin justificar por concurrencia/consulta. Reusar external-action/checkpoint durable existente si Apply demuestra identificación idempotente útil; si no, guardar únicamente el checkpoint bootstrap mínimo en proyecto.

### 5. Alta Greenfield como transacción de efectos observables, OpenSpec oficial

Antes de insertar proyecto: validar autenticación, esquema, tipo, URL/repo GitHub, rama, conexión/provider/métodos, identidad de permisos, perfiles y ZIP; verificar capacidad de branch/PR/workspace requerido con lecturas sin mutar. Un Greenfield válido crea fila `BOOTSTRAPPING` y binding durable, luego realiza filesystem/Git usando `ManagedWorkspaceGuard`, `ProjectManagedRepositoryBinding`, identidad y `WorktreeManager`; nunca modifica base. Si rama declarada falta, crearla con API GitHub/operación Git existente autorizada a partir de una base observada; fallar con evidencia si no se puede resolver la base.

Crear rama bootstrap única desde base remota confirmada. Preparar el workspace aislado, instalar/comprobar dependencias y CLI oficial `openspec` con scope del repositorio/workspace autorizado, verificar la versión real y las capacidades que expone esa versión antes de usar opciones de init/configuración; instalar/configurar para cada agente seleccionado el conjunto completo de comandos, skills y workflows oficiales disponibles y compatibles, incluidas operaciones extendidas como Verify, Sync y Archive cuando la versión las ofrezca. Verificar cada dependencia y capacidad mediante el CLI/integración oficial; no inferir nombres, flags o perfiles de versiones anteriores. Si falta un componente compatible requerido por esa distribución, fallar cerrado. No escribir wrappers ni una implementación propia de propuesta/specs/workflows. Las skills instaladas se referencian al catálogo y no se duplican.

El agente de pensamiento (CLI capaz de editar archivos, no API text-only) recibe fuentes exactas del ZIP, manifiesto/hash y las instrucciones canónicas; lee y organiza documentos/decisiones/restricciones/referencias/diagramas/assets basándose exclusivamente en ellos, conserva contenido/procedencia y entrega índice/mapa y enlaces. No produce nuevas propuestas, requisitos, historias, decisions, backlog ni análisis creativo; no resuelve contradicciones. Almacenar fuentes originales dentro del contexto de repo de modo seguro sin duplicar innecesariamente su contenido; crear índice que apunte a documento canónico en vez de replicar masivamente.

Integrar referencias concisas en `AGENTS.md` y el equivalente del agente elegido si existe, y `openspec/config.yaml`; preservar texto previo compatible y no sobreescribir instrucciones no conciliadas. Validar integridad, procedencia, links/rutas, config oficial, secretos y diff esperado. Commit solo en rama bootstrap autorizada; push y crear PR hacia la principal. Primera autorización humana de un flujo válido es revisión/approval/merge del PR. No auto-merge. Solo consulta de merge al proveedor puede marcar `PREPARED`; PR cerrado/rechazado/base/head cambiado bloquea. No iniciar tickets.

### 6. ZIP y contenido no confiables

Validar ZIP antes de fila/efectos: tamaño comprimido/expandido, cantidad/path lengths, formatos permitidos por seguridad del runner; rechazar path absoluto, `..`, colisiones tras normalizar, enlaces simbólicos/hardlinks, dispositivos, archivos ejecutables/archives anidados según policy mínima. El agente no recibe credencial GitHub ni variables secretas. Secret scanner/redaction previo a commit; contenido sospechoso o secreto bloquea y preserva cuarentena limitada, no lo sube.

Límites deben estar configurados con defaults finitos y derivarse del storage/limits existentes; si no hay policy estable, tareas de Apply determinan límite explícito antes de aceptar ZIP. No incorporar AV externa/servicio de escaneo sin evidencia del host.

### 7. Continuidad sin duplicar efectos externos

Usar clave natural `(project_id, onboarding_revision)` y relación durable exacta branch+base SHA+head SHA+PR id para observar antes de reintentar. Después de un reinicio consultar git y GitHub bajo auth del proyecto antes de crear branch/commit/PR o invocar de nuevo agente. Si la llamada al agente quedó con resultado UNKNOWN, conservar el workspace/diff y solicitar inspección/continuación controlada; no repetir operación pagada a ciegas. Un mismo ZIP/hash y revisión con PR pendiente se devuelve como operación existente; un archivo nuevo/reemplazo explícito crea revisión nueva/PR nuevo sobre main actualizada. Desfase de repo, default branch, base SHA o PR diferente produce `BLOCKED`, no retry automático.

Reusar claims/fencing/external-action sólo si se demuestra compatible con proyecto/onboarding; F2 no reactiva `SchedulerService`, no procesa Issue remoto y no introduce motor de recuperación general. Observación del merge puede ser manualmente consultada vía CLI/API, no poll scheduler.

### 8. Actualización incremental

Solo proyecto `PREPARED` y rama principal vigente. Validar ZIP y perfil antes de efectos; derivar rama única de actualización desde HEAD actual de la principal y ejecutar el mismo agente de pensamiento con contexto aprobado + nuevo paquete. El agente propone solo organización documental de la nueva fuente, mapea duplicados/complementos/reemplazos explícitos y registra contradicciones con hashes/procedencia. Cuando una fuente nueva contradice una decisión aprobada sin declarar reemplazo explícito, conserva la decisión vigente como autoritativa, clasifica y conserva el nuevo documento, registra ambas fuentes y la contradicción, e incluye ese registro en el PR para revisión humana. Esa contradicción documental por sí sola no bloquea el PR ni cambia el contexto efectivo; fallos reales de seguridad, permisos, integridad/fidelidad o publicación sí bloquean. No modifica proyecto `main`; produce commit y otro PR. Hasta que ese PR se observe merged, toda resolución/contexto del proyecto apunta al SHA previamente aprobado; candidatos de trabajo de F3 (que aún no se ejecuta en F2) nunca consumirán la rama/PR no fusionada.

Si el ZIP no tiene contenido válido, agente no puede escribir, la integridad/procedencia no puede probarse, o PR queda ambiguo, no fabricar PR ni cambiar contexto efectivo; conservar rama y estado bloqueado para recuperación.
